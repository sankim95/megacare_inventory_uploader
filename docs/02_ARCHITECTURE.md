# inventory_uploader Architecture

| 항목 | 값 |
|---|---|
| 문서 상태 | Active |
| 권위 역할 | 현재 구현의 구성 요소·데이터·상태·외부 경계 |
| 마지막 코드 대조 | 2026-08-09 |
| 대조 범위 | 백엔드, 프런트엔드, Alembic, 테스트, 실행 스크립트 |
| 미대조 | 실제 OpenAI 응답, 배포 환경, 운영 데이터 |

## 1. 설계 목표와 경계

이 시스템은 약국 한 곳의 단일 사용자가 로컬에서 사용합니다. AI는 이미지에서 구조화 초안을 만들고, 결정적 백엔드 매칭 규칙의 자동 승인 또는 사람의 수동 승인이 Excel 변경을 확정합니다.

- 원본 Excel과 원본 사진은 보존합니다.
- 신규 상품은 자동 생성하지 않습니다. 미매칭 화면에서 사용자가 명시적으로 등록한 상품만 현재 작업과 결과 Excel에 추가합니다.
- 외부 AI에는 처리 중인 이미지 한 장만 보내며 상품리스트 전체는 보내지 않습니다.
- 클라우드 DB, 다중 사용자, 로그인, POS/ERP 연동은 MVP 범위가 아닙니다.

## 2. 구성 요소

| 구성 요소 | 책임 | 주요 위치 |
|---|---|---|
| React SPA | 작업 생성, 업로드, 검수, 자동 저장, 충돌 해결, 완료 결과 표시 | `frontend/src` |
| FastAPI API | 입력 검증, mutation 차단, 상태 전이, 품목·문서 API, 요약·내보내기 | `backend/app/api`, `backend/app/main.py` |
| 도메인 서비스 | Excel, 이미지 보정, AI 추출, 매칭, 검수, 가격·재고, 중복, 복구 | `backend/app/services` |
| SQLite/SQLAlchemy | 작업, 문서, 품목, 상품 인덱스, 가격 결정, 완료 중복 이력 | `backend/app/models`, `data/app.db` |
| Alembic | 스키마 버전과 기존 DB 업그레이드 | `backend/alembic` |
| 로컬 파일 저장소 | 원본 업로드, 보정 이미지, 결과 Excel | `data/uploads`, `data/corrected`, `data/exports` |
| OpenAI Responses API | 이미지 한 장의 문서·품목 JSON Schema 추출 | `backend/app/services/extraction.py` |

개발 모드에서는 Vite가 UI를 제공하고 FastAPI가 `/api`를 제공합니다. `start.sh`는 프런트엔드를 빌드한 뒤 FastAPI가 정적 파일과 API를 한 프로세스에서 제공합니다.

## 3. 주요 데이터 흐름

```text
새 작업 화면에서 Excel·사진 로컬 선택
→ 임시저장 시 작업 생성
→ 상품리스트 .xlsx 검증·UUID 이름 저장·상품 인덱스 생성
→ 사진 원본 저장·로컬 보정
→ 작업 단위 추출 소유권 획득
→ 사진별 OpenAI 구조화 추출·실패 격리
→ 사용자 확정 OCR 별칭 재사용 또는 기존 상품 후보 매칭·경고 계산과 안전 조건 충족 행 자동 승인
→ 보류 항목이 있는 사진별 사람 검수·승인/보류/제외·가격 충돌 해결
→ 미매칭 신규 상품은 사용자가 직접 등록해 현재 작업 상품 인덱스에 연결
→ 백엔드가 최신 DB 상태로 차단 조건 재검증
→ 임시 Excel 복사본에 승인 변경·이력 기록
→ 결과 재오픈 검증
→ 원자적 결과 확정·완료 중복 이력 저장
```

## 4. 상태와 동시성

### 작업 상태

`draft → extracting → reviewing → exporting → completed`가 정상 흐름입니다. 실패·프로세스 중단은 복구 서비스가 검수 가능한 `reviewing` 또는 명시적 실패 상태로 수렴시킵니다.

### Mutation 잠금

`EXTRACTING`, `EXPORTING`, `COMPLETED`에서는 Excel·문서·품목·매칭 등 충돌하는 변경을 서버 공통 guard가 거절합니다. UI 비활성화는 편의 기능이고 서버 차단이 권위입니다.

작업 전체 삭제는 목록의 별도 확인을 거쳐 수행합니다. `EXTRACTING`, `EXPORTING` 작업은 실행 결과와 경합하지 않도록 서버에서 삭제를 거절하고, 그 밖의 작업은 완료 작업을 포함해 연관 DB 행과 `uploads`, `corrected`, `exports` 아래 해당 작업 파일을 함께 정리합니다. 완료 작업 삭제 시 해당 작업의 완료 문서 중복 이력도 제거됩니다.

### 추출 소유권

- 추출 시작은 조건부 DB update로 `EXTRACTING`과 새 `extraction_attempt_id`를 함께 획득합니다.
- 문서 결과 저장과 작업 최종 상태 변경은 같은 attempt ID를 가진 실행만 수행합니다.
- 오래된 실행은 새 실행의 데이터와 상태를 덮어쓸 수 없습니다.
- 앱 시작 시 중단된 `PROCESSING` 문서를 실패로 표시하고 작업을 `REVIEWING`으로 복구하며 attempt ID를 지웁니다.

내보내기도 기존 `export_attempt_id`와 완료 문서 unique constraint를 사용해 중복 결과·이력 확정을 방지합니다.

## 5. 데이터 모델

| 모델 | 핵심 책임 |
|---|---|
| `Job` | 작업 상태, 원본 Excel, 추출·내보내기 attempt, 승인자, 결과 경로·시각 |
| `ProductIndex` | 해당 작업의 Excel 상품코드↔행과 사용자가 직접 등록한 신규 상품의 예약 출력 행·입력값 |
| `LearnedMatch` | 정규화 OCR 코드 또는 상품명+규격과 사용자가 확정한 실제 상품코드의 작업 간 연결 |
| `Document` | 원본·보정 이미지, 처리 상태, 문서 헤더, AI 응답, 중복 상태 |
| `Item` | OCR 원문·현재값, 매칭, 기준 재고·단가, 반영 체크, 검수 상태·메모·경고 |
| `PriceResolution` | 같은 상품의 단가 후보와 자동·수동 대표 결정 |
| `CompletedDocument` | 완료된 이미지 해시, 문서 식별키, 품목 서명의 전역 중복 기준 |

현재 Alembic head는 `f7b1c2d3e4a5`입니다. 모델 enum check constraint와 완료 문서 unique constraint의 표현은 migration 결과와 일치하도록 관리합니다.

## 6. 가격·재고 계산 경계

- `+재고`는 0 이상 정수이며 `승인 AND 재고 반영` 행만 상품코드별 합산합니다.
- 기존 음수 `현재고`는 기준값으로 허용하지만 음수 `+재고`를 허용한다는 뜻은 아닙니다.
- 유효한 사진 단가가 기존 단가와 다르면 매입단가 반영을 기본 선택하고 같으면 해제합니다.
- 사진 단가 편집 요청이 체크박스를 함께 명시하면 명시 값이 우선합니다. 단가만 바꾸면 기본값을 다시 계산합니다. 메모 등 무관한 편집은 기존 선택을 보존합니다.
- 같은 상품의 여러 단가는 날짜·동일값 규칙으로 자동 결정하고 최신 날짜 내 충돌 또는 날짜 비교 불가 시 수동 결정까지 내보내기를 막습니다.
- 최종 계산과 내보내기 가능 여부는 백엔드 `summary`, `inventory`, `pricing`, `review` 서비스가 권위입니다.

## 7. Excel 경계

- 입력은 `.xlsx`, `Sheet` 시트, 필수 헤더와 유일한 상품코드를 요구합니다.
- 음수 매입단가는 업로드에서 422로 거절합니다.
- 추출 또는 검수 데이터가 존재하면 기존 작업의 Excel 교체를 409로 거절합니다. 새 Excel은 새 작업 또는 원본만 복사하는 작업 복제를 사용합니다.
- 결과는 원본의 새 복사본이며 상품코드와 행을 다시 확인한 뒤 허용된 `현재고`, `매입단가`, 이력 시트만 변경합니다.
- 사용자가 직접 등록한 상품은 현재 작업에서 예약한 새 행에만 추가하고 최종 재고·단가를 기록합니다. 원본 Excel에는 행을 추가하지 않습니다.
- 출력 재검증에 실패하면 작업 완료와 완료 중복 이력을 확정하지 않습니다.

## 8. API 시간과 UI 저장

- `/jobs/new/upload` 진입과 파일 선택은 서버 mutation을 보내지 않습니다. 사용자가 `임시저장`을 누르면 중복 클릭을 막은 상태에서 작업을 한 번 생성하고 작업 URL로 전환한 뒤, 선택한 Excel과 사진을 순서대로 저장합니다.
- 임시저장 후 기존 작업의 파일 추가·교체와 AI 추출 이후 검수 편집은 기존 저장 정책을 유지합니다.
- DB 시간은 UTC 기준으로 생성합니다.
- Pydantic의 `UtcDateTime` 직렬화가 naive SQLite datetime도 UTC로 해석해 `Z`가 있는 ISO 8601을 반환합니다.
- 목록과 완료 UI는 `Asia/Seoul`로 표시합니다.
- 검수 화면의 품목 저장은 행별 Promise queue로 직렬화합니다. 행별 version이 최신 요청의 응답만 화면에 반영하게 하며, 실패 시 서버 최신 품목을 다시 읽습니다.
- 수동 후보의 `선택·반영`은 `PUT /items/{item_id}/match`의 선택적 `approve` 입력으로 매칭과 승인 의도를 한 트랜잭션에서 처리합니다. 유효한 `+재고`가 없으면 매칭만 저장하고 보류를 유지하며, 재고·단가 반영 체크는 변경하지 않습니다.
- 수동 매칭은 OCR 원본·현재 코드와 상품명+규격 별칭을 전역 기록합니다. 이후 작업에서는 저장된 상품코드가 그 작업의 기준 Excel에 존재할 때만 자동 적용하며, 사용자가 수동 매칭을 해제하면 해당 품목에서 학습한 연결도 제거합니다.
- 미매칭 품목의 `POST /items/{item_id}/register-product`는 사용자가 입력한 상품을 현재 작업 `ProductIndex`에 추가하고 즉시 매칭합니다. 다른 작업에서 사용하려면 이 작업의 결과 Excel을 다음 기준 Excel로 업로드해야 합니다.
- 원본 사진 보기는 `GET /documents/{document_id}/image?variant=original`을 사용하고, 클릭 회전은 저장 데이터를 바꾸지 않는 프런트엔드 표시 상태입니다.
- 작업 집계의 상품 선택은 별도 경로 이동이나 스크롤 대신 같은 집계 패널을 좌우로 분할하고, `item_ids`의 관련 행을 우측에서 전환·편집합니다. 1100px 이하에서는 두 영역을 세로로 배치합니다.

## 9. 보안·운영·복구

- `OPENAI_API_KEY`는 `.env` 또는 환경변수에서만 읽고 DB·로그·Excel에 저장하지 않습니다.
- 기본 API 바인딩은 `127.0.0.1`입니다.
- 업로드 실제 파일명은 UUID를 사용합니다.
- 앱을 종료한 상태에서 `data/` 전체를 함께 백업·복구해야 DB와 파일 경로가 일치합니다.
- `dev.sh`, `start.sh`는 앱 시작 전에 `alembic upgrade head`를 실행합니다. 사용자 데이터가 있는 환경에서는 백업 확인이 선행되어야 합니다.

## 10. 알려진 한계

- OpenAI 추출 품질과 공급사별 양식 차이는 결정적 테스트만으로 보장되지 않으며 대표 실제 이미지 평가가 필요합니다.
- 기존 Excel의 소수점 매입단가는 원값으로 인덱스에 보존되지만 정수 기반 매칭 기준 단가로는 사용할 수 없습니다. 제품 정책은 미결정입니다.
- 이 프로젝트는 현재 Git 저장소가 아니므로 변경 이력과 롤백을 commit 단위로 추적할 수 없습니다.
